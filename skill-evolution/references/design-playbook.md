# RSI 自改进工作流设计手册

> 本文档是「技能进化（知行环）」（`skill-evolution`）的参考文档，覆盖**闭环 ① 选域 + 全链设计**（RSI 那一半）。
> 输出的方案必须落到 WikiSkill 那一半（`.wiki/` 三层 + 四问门控）才闭环——
> 本手册第 3 步与第 4 步就是两个半边的接口。

将 RSI 方法论落到用户具体项目的可执行指南。配合 `SKILL.md` 的闭环速查使用。

## 五步设计流程

### 第 1 步：定位现状（自主权分级）
- 列出用户项目中"人类手动做的改进动作"与"AI 已自动做的改进动作"
- 对照 L1–L5 表判定当前所处级别
- 输出：当前级别 + 下一步目标级别 + 人类介入下限

### 第 2 步：选落地切口

先用 **HCI** 定域（回答"往哪投"），再用三因素定任务（回答"投哪个"）。

**第一层：按 HCI 定能力域**（数值见 `rsi-framework.md`）——HCI 越低越优先：

| HCI 区间 | 域 | 建议 |
|---------|----|------|
| < 60 | 软件工程 52.6、工具调用 Agent 39.9、搜索与终端 56.8 | ✅ **首选**：缺口大、红利高 |
| 60–80 | 广博知识、法律推理、多模态推理、前沿学术广度 | ⚪ 次选 |
| > 85 | 网络安全 Agent 91.9、前沿数学 86.4、研究生级科学 85.8 | ❌ 已饱和，投入产出低 |

**第二层：按三因素选具体任务**（决定 RSI 速度）：
- **反馈成本**：获得反馈是否廉价？（编译/测试/回归 = 低）
- **可验证性**：成功与否是否明确可判定？
- **部署约束**：部署链路是否短、风险是否可控？

优先选三项都优的任务，例如：代码编译修复、单元测试生成、回归测试、日志/报错诊断、文档生成。
避免选反馈稀缺或验证冒险的领域（科学研究、机器人、医疗——RSI 论文指出这三者进展明显更慢）。

### 第 3 步：设计闭环（套四步）
1. **重构环境**：标准化工作区为可复现的训练/评估环境（固定依赖、可重跑测试套件、隔离沙箱、结构化日志）
2. **暴露缺口**：让 AI 在该环境反复执行任务，记录失败模式 → 生成"难例数据集"
3. **再训练/沉淀**：把修通过的 pattern 沉淀为可复用经验。**推荐直接复用本 skill 的沉淀层实现**——其 `.wiki/` 三层架构（Raw 执行轨迹 → Wiki 持久化知识 → Skill 可回滚执行指令）已是 RSI「四大追问」中可保持/可迁移/可回滚的工程化身，且与平台无关：WorkBuddy / Claude Code / Codex 共享同一 `.wiki/` 目录，经验可随项目提交 Git 跨电脑迁移。若目标项目尚未初始化，先 `wiki init` 再对接。
4. **迭代环境**：用更强/更懂的 AI 提升环境本身（更优测试、更准的验证器、更全的回归集）

### 第 4 步：定义验收（四大追问 → 门控评分卡）

这一步是**两个半边的接口**：把 RSI 的四问翻译成 WikiSkill 门控要用的证据。

| 追问 | 设计阶段要预先写清 | 门控阶段拿什么判定 |
|------|------------------|------------------|
| **可衡量** | 用哪个独立指标 / 独立评估？基线是多少？ | ≥2 个同域任务用同一判据复测 |
| **可保持** | 经验存哪（`.wiki/knowledge/`）？何时复测？ | 间隔一个复盘周期后仍成立 |
| **可迁移** | 预期复用范围（本项目 / 跨项目 / 跨平台）？ | ≥1 个不同任务域或另一平台成功 |
| **可回滚** | 版本化手段（技能「变更历史」/ git / 备份）？ | 能恢复到上一版，否则一票否决 |

> 判定规则与后果见 `workflow.md`「门控机制」——那里是评分卡的**唯一权威源**，
> 本表只讲"设计阶段该预先写清什么"。别在两处各写一套标准。

**关键**：验收标准必须在**提案之前**写好。事后定义的成功标准不算数——
这正是「可衡量」追问要防的自欺。

### 第 5 步：输出方案
产出结构化方案文档（模板见下），含：现状级别、切口选择理由、闭环设计、验收标准、风险与回滚。

## 问诊清单（执行前问用户）
1. 目标项目/代码库路径与核心技术栈？
2. 当前哪些改进动作是人工重复做的？
3. 该任务能否自动化获得明确反馈（测试/编译/评分）？
4. 期望达到 L 几？可接受的人类介入下限？
5. 是否有独立评估手段验证改进真实有效？

- 为什么不选其他域：<…>

## 典型示例（独立开发者场景）
- **AI Coding 助手自改进**：把编译/测试报错标准化为环境 → AI 反复修 → 修通过的 pattern 沉淀进项目级 skill → 下一轮用更强模型提升测试覆盖
- **SaaS 项目运维自改进**：把 Redis 迁移/接口报错日志结构化为反馈 → Agent 诊断并沉淀修复经验
- **数据质量保障**：交付后真实反馈驱动更新 → 关键缺陷率下降、人工处理时间缩短（参考 Humanlaya 9.0%→3.7%）

## 通用性与跨平台约束（必须遵守）
- 本 skill 输出的方案保持**平台中立**：不假设只在 WorkBuddy 运行，也不硬编码任何工具私有目录（如 `~/.workbuddy/`）。
- 经验沉淀统一走本 skill 的 `.wiki/`（项目自包含、可提交 Git、跨机器迁移），使同一套自改进闭环在 Claude Code / Codex / WorkBuddy 等任意 agent 下都能运行。
- 引用其他 skill 的资源时，使用其项目内相对路径，而非工具私有绝对目录。

## 注意事项
- 不要承诺 L5 级递归收益（缺乏充分验证），现实目标通常是 L2–L3
- 强调"独立评估"，反对自评分刷榜
- 经验沉淀优先复用本 skill 的 `.wiki/`（跨平台、带验证-回滚），不另造轮子、不锁定单一 agent
